ℹ️ O caminho “dois saltos” dos segredos é intencional

Citando docs/process/07-security-audit.md: “GitHub Secrets remains the source of truth Terraform reads from at apply time; Secrets Manager is what the running ECS task reads at container start; this two-hop path is intentional and standard for Terraform-managed secrets.” Ou seja: GitHub Secrets → Terraform apply (grava no RDS e no Secrets Manager) → ECS task resolve do Secrets Manager no boot. O container nunca recebe o segredo via variável de ambiente comum.

⚠️ Atenção — antes vs. depois (07-security-audit.md)

Antes do audit de 2026-08-07, SECRET_KEY e POSTGRES_PASSWORD iam em texto puro direto do GitHub Secret para o bloco environment da task definition (visíveis a qualquer um com ecs:DescribeTaskDefinition). O Secrets Manager e o SSM Parameter Store estavam completamente vazios na conta antes disso. A correção (já aplicada e vigente) moveu os dois para o bloco secrets: via Secrets Manager, como mostrado na tabela acima.

Por que "SameSite=None" e um endpoint de bootstrap de CSRF?

Web e API rodam em domínios CloudFront diferentes (d1qdib1mcwro0s... vs d1ukfp2c7u1v45...) — não há subdomínio compartilhado nem cookie de app comum. Isso cria dois problemas resolvidos em docs/process/10-csrf-cross-origin-fix.md:

  1. Cookies SameSite=Lax (padrão do Django) não são enviados em POSTs cross-site — o navegador simplesmente omite o csrftoken na requisição para a API, e o Django rejeita com 403 mesmo que o header esteja certo.
  2. document.cookie só enxerga cookies do próprio domínio (o do frontend) — o csrftoken setado pela API nunca é legível via JS na SPA.

Solução implementada (backend + frontend, shipada em develop): o backend alinha CSRF_COOKIE_SAMESITE/SESSION_COOKIE_SAMESITE ao mesmo COOKIE_SAMESITE das JWT, e o endpoint GET /api/auth/csrf/ retorna o token também no corpo JSON ({"csrfToken": "..."}), não só no cookie. O frontend guarda esse token em memória e o envia via header X-CSRFToken em toda requisição que não seja GET/HEAD/OPTIONS/TRACE.

Detalhes de implementação

Backend (apps/accounts/authentication.py)

CookieJWTAuthentication estende JWTAuthentication do SimpleJWT: se vier header Authorization: Bearer, usa o fluxo padrão (sem CSRF — pensado para clientes CLI/mobile). Se vier só o cookie access_token, valida o JWT e chama enforce_csrf() manualmente — porque o APIView do DRF desliga o middleware de CSRF do Django por padrão, então a autenticação por cookie precisa reimpor essa proteção.

Frontend (src/lib/api.ts)

Cliente fetch fino, sem contexto de auth nem hook useAuth. Toda chamada usa credentials: "include". Para métodos não seguros (tudo exceto GET/HEAD/OPTIONS/TRACE), chama ensureCsrfToken() que reusa o token em memória ou busca via /api/auth/csrf/, e injeta X-CSRFToken. Nunca guarda JWT em localStorage/sessionStorage.

CORS — travado por ambiente

AmbienteCORS_ALLOWED_ORIGINS / CSRF_TRUSTED_ORIGINS
Localhttp://localhost:3000 (+ 127.0.0.1:3000)
Staginghttps://d1qdib1mcwro0s.cloudfront.net — somente a origem do web CloudFront desse ambiente
Prod (quando existir)a URL do web CloudFront/domínio daquele stack — nunca a de staging, nunca *

CORS_ALLOW_CREDENTIALS = True com CORS_ALLOW_ALL_ORIGINS = False — combinação obrigatória (credentials + wildcard é rejeitado pelo próprio django-cors-headers). Uma função de guarda em config/settings.py (_assert_deployed_origin_allowlist) recusa subir com ENVIRONMENT em staging/production se a allowlist estiver vazia, tiver wildcard ou contiver localhost.

ℹ️ Login/lockout e throttling

django-axes bloqueia após 5 tentativas de login falhas (AXES_FAILURE_LIMIT=5, cooldown de 1h). DRF aplica throttle de 20/minuto no escopo auth (register/login/refresh) e 50/hora anônimo / 1000/hora autenticado nos demais endpoints.

ℹ️ Por que o frontend não usa container na AWS

O Next.js do projeto roda em modo output: "export" (site 100% estático, sem SSR/API routes) — não há nada em runtime que exija Node.js rodando. Por isso o Terraform aponta para S3 + CloudFront em vez de outro serviço ECS: é mais barato, sem servidor para corrigir/atualizar, e a aws_cloudfront_function.web_spa_rewrite resolve o roteamento client-side que o nginx local faz via nginx.conf.
